# HealthGuard AI — Review 1

An explainable multi-disease risk platform built on one claim:

> Accuracy is the least interesting property of a clinical model. A
> deployable decision-support system has to answer three questions —
> **Can I trust this number? Why this number? What do I do about it?**

Four diseases (heart, diabetes, chronic kidney disease, stroke), four
calibrated models, SHAP explanations, guideline-cited action plans, and a
React interface that shows how much of each prediction rests on values
the patient never supplied.

---

## Run it

Two terminals. Python 3.10+ and Node 18+.

**Terminal 1 — backend**

```bash
pip install -r requirements.txt

python -m src.data.generate_standins   # skip if using the real CSVs
python -m src.data.clean
python -m src.data.audit
python -m src.models.train             # ~3-4 minutes

uvicorn src.api.main:app --reload --port 8000
```

**Terminal 2 — frontend**

```bash
cd frontend
npm install
npm run dev                            # http://localhost:5173
```

Vite proxies `/api` to port 8000, so no CORS configuration is needed.

### Swapping in the real datasets

Put the real CSVs in `data/raw/` with these exact filenames:

| File | Source |
|---|---|
| `heart.csv` | UCI Cleveland Heart Disease |
| `diabetes.csv` | Pima Indians Diabetes (NIDDK) |
| `kidney.csv` | UCI Chronic Kidney Disease |
| `stroke.csv` | Kaggle Healthcare Stroke Prediction |

Then delete `data/raw/STANDIN_MARKER.json` and re-run `clean` → `audit` →
`train`. **No code changes.** The stand-in generator reproduces the real
column names, encodings and defects precisely so the pipeline transfers.

## The two findings that carry the project

### 1. Only 1 of 6 core fields exists in all four datasets

Generated by `src/data/clean.py`, written up in `docs/dataset_audit.md`:

| Core field | Heart | Diabetes | Kidney | Stroke |
|---|---|---|---|---|
| `age` | direct | direct | direct | direct |
| `sex` | direct | **constant** (female-only) | **absent** | direct |
| `systolic_bp` | direct | **proxy** (diastolic) | **proxy** (diastolic) | **absent** |
| `bmi` | **absent** | direct | **absent** | direct |
| `glucose` | **proxy** (binary flag) | direct | direct | direct |
| `smoking` | **absent** | **absent** | **absent** | direct |

Only `age` is measured directly and comparably everywhere. The standard
version of this project feeds one patient vector into four models as if
this were not true. We measured it instead, and designed around it:
every disease is trained twice, full-feature and core-only, and the
accuracy gap between them is reported.

### 2. Neither clinical baseline is fully computable on public data

- **Framingham** (BMI-based variant) needs BMI and smoking status. UCI
  Heart records neither → runs at **4 of 7 inputs**.
- **FINDRISC** needs waist circumference, physical activity, diet and
  family history. Pima records none → runs at **3 of 8 inputs**, with a
  maximum of 19 points instead of the published 26.

Every call returns an `ItemReport` naming exactly what was substituted.
This is independent evidence that these datasets are not fit for the
CDSS people routinely build from them.

### And calibration measurably works

| Disease | ECE before | ECE after | Method chosen |
|---|---|---|---|
| Stroke | 0.277 | **0.0045** | sigmoid |
| Diabetes | 0.142 | **0.026** | sigmoid |
| Kidney | 0.092 | **0.045** | sigmoid |
| Heart | 0.093 | **0.071** | sigmoid |

A 60× improvement on stroke. This is the number that proves the step
wasn't decorative.

## Read this before quoting any figure

Two caveats, both of which you should raise *before* an evaluator does.

**Stand-in data.** Labels were generated from a linear logit over each
dataset's own features, so logistic regression is the true model and wins
everywhere. **On the real datasets that ordering will very likely
reverse.** Model-vs-clinical-score comparisons are also not meaningful on
stand-in data, because our models see the exact features the labels came
from and Framingham does not. `artifacts/metrics.json` carries these
caveats in `data_provenance`, and the UI displays them.

**Stroke recall at threshold 0.5 is 0.057.** That is not a broken model —
it is what a correctly calibrated model does at 5% prevalence. Quote the
operating points instead: at threshold 0.18, recall is 0.547 with
precision 0.333. Full cost-sensitive threshold selection and decision
curve analysis are Review 2.

### The protocol, in one paragraph

Hold out a stratified 20% test set first and touch it once. Put
imputation, scaling and encoding *inside* the sklearn Pipeline so they
refit per fold — this is why our numbers are lower and more trustworthy
than the 90-95% commonly reported. Compare three candidates by
5×5 repeated stratified cross-validation and report mean ± std. Handle
imbalance with class weights, not SMOTE. Select by average precision.
Calibrate with both sigmoid and isotonic and keep whichever has the lower
out-of-fold Brier score.

## Review 1 demo script (5 minutes)

1. **"The standard version of this project has three flaws."** Mismatched
   datasets, a meaningless averaged score, accuracy figures that indicate
   leakage. *(45s)*
2. **Coverage matrix.** 1 of 6. Here is what we found. *(45s)*
3. **Clinician view.** Model table, calibration curves, the ECE
   improvement, the clinical baseline row with its availability figure.
   "We report an honest number, and here's why it's the trustworthy
   one." *(60s)*
4. **Patient view.** Load the elevated-risk example → four risks with
   certainty strips → the scope warning firing for a male patient →
   SHAP → the action plan with citations. *(90s)*
5. **Drag the BMI slider.** Everything recomputes live. *(30s)*
6. **Roadmap.** Review 2 adds conformal intervals and abstention, DiCE
   counterfactuals, decision curve analysis, a fairness audit, and the
   PDF report. *(30s)*

Rehearse it. Start both servers before you walk in. Keep a screenshot
deck as a fallback — more projects lose marks to a live crash than to
weak methodology.
